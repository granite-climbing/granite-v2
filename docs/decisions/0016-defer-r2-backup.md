## Context

D1은 [ADR 0004](0004-cloudflare-d1-as-database.md)에 따라 일 1회 export 후 R2 backup bucket에 7일 보관한다. 그렇다면 R2 자체에 대한 추가 백업(예: 다른 리전 또는 다른 클라우드로 복제)도 필요할 수 있다.

그러나 R2에 저장되는 데이터는 다음과 같다.

- Crag/Sector/Boulder/Topo/Route 커버 및 라인 이미지
- 공지(Announcement) 커버 이미지
- 사용자 아바타
- Instagram/YouTube 베타 썸네일 (원본은 외부 플랫폼에 존재)

이 중 사용자 본인이 업로드한 유일본은 사실상 아바타뿐이고, 나머지는 관리자가 큐레이션한 콘텐츠 또는 외부 원본에서 재수집 가능한 파생물이다. 즉 **데이터 민감도와 비가역성 모두 낮다**.

## Decision

MVP 단계에서는 R2 백업을 별도로 진행하지 않는다.

- D1 → R2 backup bucket의 일일 export는 그대로 유지.
- R2 객체는 UUID 기반 키로 덮어쓰기를 방지 ([ADR 0005](0005-r2-and-image-cdn-pipeline.md)).
- Cloudflare R2 자체의 가용성/내구성에 의존한다.
- 손실 발생 시 복구 절차:
  1. 콘텐츠 이미지: 운영자 로컬 원본에서 재업로드 (관리자에게 원본 보관 권장).
  2. 베타 썸네일: `betas.media_url` 기반으로 재수집 시도.
  3. 아바타: 사용자에게 재업로드 안내.

## Transition trigger

다음 중 하나가 발생하면 R2 백업 도입을 재검토한다.

- 사용자 생성 콘텐츠(UGC)가 도입되어 비가역 데이터가 늘어남.
- Cloudflare R2 장애로 실제 복구 시나리오가 발생.
- 운영자 로컬 원본 보관 정책이 깨지거나 운영 인원 구조가 바뀜.
- 법적/규제 요구사항으로 별도 보관이 필요해짐.

## Consequences

- 운영 비용·복잡도 감소.
- R2 장애 시 일부 이미지 손실 가능성을 수용. 사용자 영향은 "이미지가 보이지 않음" 수준에 그침 (데이터 모델 자체는 D1 백업으로 복구 가능).
- 관리자에게 콘텐츠 이미지 원본을 로컬에 보관하도록 운영 가이드에 명시 필요.

## Alternatives considered

- **R2 → 별도 리전 R2 복제**: 비용·운영 부담 대비 이점 작음.
- **R2 → 외부 클라우드(예: S3) 미러링**: 멀티클라우드 운영 부담.
- **즉시 백업 도입**: 현재 데이터 민감도에 비해 과투자.
